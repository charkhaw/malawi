# 2. Service Specifications, Supply and Install Items

## 2.1 System integration

| Requirement | Technical reasons supporting compliance | Cross-references |
|---|---|---|
| **2.1.1** End-to-end integration services for seamless data exchange between NRIS and the Personalization and Mailing System | Complies. A single integration gateway, held by the Data Preparation Service, carries every exchange with NRIS: production requests, secure demographic and biometric transfer, personalization and issuance, quality and production monitoring, mail processing and dispatch, status tracking and reporting, reprint and replacement, and audit and traceability. Inkript accepts single-point responsibility for the integration. | System Architecture Sections 1.2, 6.4 and 7.1 |
| **2.1.3.1.1** Design, develop, test and deploy NRIS interfaces supporting REST, SOAP, file transfer, queues and database integration | Complies. Inkript designs each interface in an Interface Control Document and develops, tests and deploys its production side over REST APIs, SOAP web services, secure file transfer, message queues and middleware, or database integration. As clarified in the Responses to Queries 003 and the Clarifications to Queries 005, NRB developers build the NRIS side and the Purchaser provides its API. | System Architecture Sections 7.1, 7.2 and 13.1; Preliminary Project Plan Section 2.5 |
| **2.1.3.2.1** Analyze NRIS data structures, map fields, develop transformation rules, implement validation and cleansing | Complies. NRIS data is analyzed in discovery by data dictionary review and profiling of NRIS test data. Each field is mapped in the Data Mapping and Transformation Document, transformation rules for dates, names, images and addresses are applied in one place, and every record is validated before queuing, with failures held and reported to NRIS. | System Architecture Section 7.3; Preliminary Project Plan Section 2.3 |
| **2.1.3.2.2** Exchanged data elements: listed demographic, biometric and card data | Complies. The field-level mapping carries demographic data (National ID Number, names, date of birth, gender, nationality, address, district, Traditional Authority and card serial number, which the System returns to NRIS), biometric data (facial image, fingerprint references, signature image) and card data (issue date, expiry date, type and status). | System Architecture Section 7.3 |
| **2.1.3.3.1** Secure exchange: end-to-end encryption, TLS, certificates, PKI authentication, integrity validation, key management | Complies. All exchanges run over TLS 1.2 or higher, personal and biometric payloads are encrypted end to end, both systems authenticate each other by PKI certificates rather than shared secrets, every exchange carries an integrity check, and interface keys are held in protected storage with controlled access and scheduled rotation. | System Architecture Sections 7.4, 10.5 and 13.1 |
| **2.1.3.4.1** Configure middleware, orchestration workflows, message routing, exception handling and retry mechanisms where required | Complies. Middleware is configured where an exchange needs routing, translation or decoupling. Orchestration workflows sequence multi-step exchanges, messages are routed by content and type, failed exchanges are held and raised rather than discarded, and retries run on a defined schedule with a limit, after which the exchange becomes a recorded exception. | System Architecture Sections 7.2 and 7.12 |
| **2.1.3.5.1** Secure NRIS database connectivity, read-only and transactional interfaces, synchronization and performance optimization | Complies. Where the Purchaser approves it, database connections run encrypted from defined hosts under named service accounts, read-only for retrieval and transactional where write access is approved, with scheduled synchronization and queries indexed to production access patterns. As clarified in the Clarifications to Queries 005, the main route is the NRIS API the Purchaser provides. | System Architecture Sections 7.5 and 13.2 |
| **2.1.3.6.1** Support real-time transactions and batch processing for requests, status, alerts, reprints and historical data | Complies. Card production requests, card status updates and production alerts are exchanged in real time. Daily production batches, bulk reprints and historical data synchronization run as scheduled batches, using secure file transfer where suited. Both modes write to the same records and audit trail, so each card has one history. | System Architecture Sections 7.2 and 7.6 |
| **2.1.3.7.1** Implement transaction logging, security logging, audit trail synchronization and user activity tracking | Complies. Every boundary exchange is logged with direction, payload reference, outcome and time. Authentication, certificate and access events are security-logged, operator and administrator actions are tracked by named identity, and production audit records are aligned with the NRIS audit trail. Audit records are tamper-proof and time-synchronized. | System Architecture Sections 7.14 and 10.6 |
| **2.1.3.7.2** All transactions traceable from NRIS through card production and mailing | Complies. Every record is keyed to the National Identity Number and the card serial number, and every stage writes against that key. A card is traceable from the retrieved NRIS request through validation, preparation, signing, marking, verification, packaging and dispatch to delivery confirmation, and blank card states are also published to NRIS. | System Architecture Sections 6.10 and 7.14 |
| **2.1.3.8.1** Integrate with NRIS disaster recovery, support failover and ensure continuity of card production | Complies. Interfaces are configured against the NRIS recovery endpoints as well as the primary, interface components run on the clustered platform with automatic failover, and retrieved work keeps being produced while NRIS is unavailable. As clarified in the Clarifications to Queries 005, the secondary environment is provisioned at the existing NRB disaster recovery site in Blantyre. | System Architecture Sections 7.15 and 9.3; Cybersecurity Risk Management Plan Section 8.1 |
| **2.1.4.1.1** Receive NRIS production requests and automatically validate, queue, batch and generate production jobs | Complies. The Data Preparation Service retrieves requests released by NRIS and checks each against the database, so none is queued twice. Records are validated, queued, assembled into batches of configurable size, 500 to 1,000 cards in normal operation, and prepared into print-ready jobs released to a production line. | System Architecture Sections 6.2, 6.4 and 7.7 |
| **2.1.4.2.1** Retrieve approved records, biographical data, photograph, signature and issuance information from NRIS | Complies. For each released record the System retrieves the approved citizen record, biographical information, the photograph, checked against ICAO size and resolution specifications, the signature image and card issuance information over the secured exchange. Data is held only while production needs it, so the facility keeps no second copy of the register. | System Architecture Sections 7.8 and 10.2 |
| **2.1.4.3.1** Generate personalization data and layouts, print and laser engrave, encode barcode data (as amended) | Complies. As amended by Addendum No. 2 and clarified in the Response to Clarifications 001, the cards are chipless. The Data Preparation Service binds each record into the approved template, the laser engraves all visual and personalization data within the card body, and the digitally signed biometric QR code is encoded as the machine-readable element. | System Architecture Sections 4.5, 6.3 and 7.9; Attachment: Laser personalization system datasheet |
| **2.1.4.4.1** Verify printing, engraving and machine-readable elements, reject defective cards, update NRIS on outcomes | Complies. Engraved data is read by optical character recognition and checked against the source record, engraving quality is assessed against acceptance thresholds, and the QR code is compared byte for byte with the signed payload. Failing cards are diverted and recorded with a reason, and every outcome is reported to NRIS. | System Architecture Sections 3.6, 6.8 and 7.9; Attachment: Laser personalization system datasheet |
| **2.1.4.5.1** Integrate with NRIS to manage new, replacement, duplicate, lost, damaged and cancelled cards | Complies. Each transaction is identified by the type on the NRIS record. New, replacement, duplicate, lost and damaged card requests are produced, with superseded cards flagged in NRIS, and a cancellation flags the record and withdraws any card in production. A unique card serial number distinguishes each physical card. | System Architecture Sections 2.3 and 7.10 |
| **2.1.4.6.1** Automatically update NRIS on each production status, from job received to delivered or rejected | Complies. Status is published to NRIS automatically, without operator action, for job received, card in production, quality control completed, card personalized, card packaged, card dispatched, card delivered and card rejected. Each event carries the National Identity Number, card serial number, job and time. | System Architecture Sections 6.4 and 7.11 |
| **2.1.4.7.1** Integrate mailing with NRIS: mail pieces, labels, envelope personalization, address validation, dispatch tracking | Complies. The Mailing and Dispatch Management System supplies each mailing line with carrier content and destination drawn from the NRIS record, generates mail pieces and dispatch batch labels, prints the address and dispatch reference on the carrier behind the envelope window, validates destination data before printing, and tracks each mail piece. | System Architecture Sections 5.3, 5.7, 6.9 and 8.6 |
| **2.1.4.8.1** Provide dispatch status updates, batch tracking, consignment tracking and delivery confirmation updates | Complies. A dispatch record is created for every mail piece, pieces are grouped into dispatch batches tracked as consignments with a handover record, and status advances by event to dispatched, delivered and available for collection. As clarified in the Clarifications to Queries 005, Inkript engages the postal operator and connects the System to its tracking service. | System Architecture Sections 8.1, 8.2, 8.3 and 8.6 |
| **2.1.4.8.2** Feed dispatch and delivery status information back into NRIS | Complies. Card packaged, card dispatched and card delivered events are sent to NRIS over the single interface, each attributable to one physical card, and advance the NRIS document tracker that sends the cardholder SMS. Events raised during an interface outage are held and published in order on recovery. | System Architecture Sections 7.15, 8.3 and 8.4 |
| **2.1.4.9** Reprint and exception management (RFP gives the heading only, with no requirement text) | Complies. Reprint requests from NRIS follow the standard production path and produce a card with a new serial number, while in-job rejects are reproduced within their job. Unreachable interfaces, exhausted retries, failed validation, incomplete records, withdrawn cards and duplicate requests each follow a defined handling path and are recorded against the affected record. | System Architecture Sections 3.7 and 7.12 |
| **2.1.4.10.1** Reporting integration: daily volumes, issuance statistics, rejection rates, throughput, mailing performance, SLA compliance | Complies. Production data is made available to NRIS reporting for daily volumes by line and shift, issuance statistics by transaction type, rejection rates with reasons, personalization throughput against the contractual rate, mailing performance and SLA compliance. Reports draw on the card-level records that drive status feedback, so figures reconcile. | System Architecture Sections 6.11 and 7.13 |
| **2.1.5.1** Interface testing: API testing, data validation testing and error handling testing | Complies. Every operation on every interface is tested against its Interface Control Document, field-level validation covers type, length, permitted and boundary values, and each documented error condition is induced. Testing runs against simulators from week 9 and against the NRIS test environment from week 18. | System Architecture Section 7.16; Preliminary Project Plan Sections 4.1 and 4.4 |
| **2.1.5.2.1** System integration testing of end-to-end data flow, process orchestration and exception handling | Complies. System integration testing in weeks 23 and 24, with NRB developers, verifies end-to-end data flow from request retrieval to delivery confirmation and orchestration across the full production sequence, and exercises exception handling by inducing each defined exception condition rather than by inspection. | System Architecture Section 7.16; Preliminary Project Plan Section 4.4 |
| **2.1.5.3.1** Performance testing of throughput, batch processing capacity and concurrent transaction processing | Complies. Performance testing verifies throughput against the required production rate, batch processing at the daily volume and concurrent transactions at expected load, at the contracted volumes rather than a reduced scale, through throughput benchmarks, load, stress, transaction integrity and sustained operation tests. | System Architecture Sections 7.16 and 11.6; Preliminary Project Plan Section 4.4 |
| **2.1.5.4.1** Security testing: vulnerability assessment, penetration testing, authentication testing and encryption validation | Complies. Vulnerability assessment covers the integration components and hosts. An independent third party penetration-tests the full deployed configuration in week 24, with retest in weeks 25 and 26. Authentication testing confirms that invalid and expired certificates and unauthenticated requests are refused, and encryption validation confirms that weak protocols and ciphers are rejected. | System Architecture Section 7.16; Preliminary Project Plan Section 4.4; Cybersecurity Risk Management Plan Section 6.2 |
| **2.1.5.5.1** Support NRIS stakeholders in user acceptance testing of workflows, functions and reports | Complies. In weeks 24 and 25, NRIS stakeholders validate business workflows, functional requirements and reporting requirements against the live integration, supported by the Supplier with test data preparation, scenario walkthroughs, defect triage and retesting. The outcome is recorded in the User Acceptance Test report. | System Architecture Section 7.16; Preliminary Project Plan Sections 4.1 and 4.4 |
| **2.1.6.1** Provide the thirteen listed integration deliverables, from strategy to knowledge transfer materials | Complies. All thirteen are provided: integration strategy and methodology, detailed architecture, Interface Control Documents, API specifications, data mapping and transformation documents, security design, test plans and scripts, integration, performance and security test reports, as-built integration documentation, operations and maintenance manuals, and knowledge transfer and training materials, in editable format and PDF. | System Architecture Section 7.17; Preliminary Project Plan Section 2.10 |
